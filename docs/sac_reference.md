# 开源 SAC 实现对照

## 目的和边界

核验当前纯 SAC 更新与成熟开源实现，避免把实现/训练预算问题误判为场景没有价值。当前主线的最终目标仍是：SAC 从零预训练，再开放 PPO，两层异频同步学习。本次只执行第一阶段的实现对照，不自动进入联合训练。

不引入 QA、教师数据、行为克隆、SCA 锚定、残差门控、奖励 shaping、多智能体或历史 checkpoint。物理环境、104 维聚合观测、18 维原始动作到 simplex 路由的映射、任务代价和时间折扣全部不变。纯 SAC 决定路由，CPU/带宽仍由公开的环境调度规则分配。

## 固定版本

- Python：本机 3.9，项目 `.venv` 继承已安装 PyTorch，不覆盖原环境。
- Stable-Baselines3：2.7.0。
- Gymnasium：0.29.1。
- 实际使用 [SB3 SAC.train 源码](https://github.com/DLR-RM/stable-baselines3/blob/v2.7.0/stable_baselines3/sac/sac.py)，不复制后悄悄改写优化步骤。
- 构造后逐层复制本次从零初始化的权重，使两臂初始网络函数相同；不从历史文件加载权重。
- 用共享 replay 的只读采样视图传入逐样本物理折扣；库的更新实现不修改。普通服务帧 discount=0.99，跨部署间隙为 0.99^3。真实 next_state 来自重置前的下一服务决策点。
- 此适配只调用 SB3.train，不调用 SB3.learn。数据仍由共享物理 collector 产生，因此不是对整个 SB3 Gymnasium rollout 系统的复现。

## 先数值核验，后开训

固定合成 batch，明确它不是真实 Q 值标签：

1. 核对同初始权重的 Q 输出、同随机噪声的动作、log-probability。
2. 捕获安装库实际 train 调用中的 target，与当前公式计算值对照。
3. 核对 Critic 梯度、Actor 梯度、温度损失。Critic 损失的已知倍数须先对齐。
4. 检查普通折扣、部署折扣、零 bootstrap 三种情形；绝对误差均须小于 0.001。
5. 检查 replay 的动作列是实际生成 transition 的原始 SAC 分数，另外保存执行路由。两者不能读错。
6. 检查采样和评估不改变环境随机流，以及两臂微型运行更新次数一致、宏观权重完全不变。

核验不过不训练；核验通过也不代表算法已能收敛。

## 两臂与共同预算

| 项目 | 固定设置 |
|---|---|
| 宏观控制 | 动态质心，不更新 PPO |
| 臂一 | 原 DirectHRL SAC 更新实现 |
| 臂二 | SB3 原生 SAC 更新实现 |
| 网络 | 两层 256 ReLU，初始权重逐层匹配 |
| 初始化 | 本次 seed=1 从零生成；初始均值 0，log_std=-2，alpha=0.05 |
| 学习率 | Actor/Critic/温度均为 0.0003，两臂相同 |
| 更新密度 | 每个服务帧一次 Critic 和 Actor 更新，1000 条 replay 后开始 |
| warmup | 两臂同一私有 RNG 均匀采样原始动作，不是教师动作 |
| batch / replay | 128 / 100000，两臂相同 |
| 训练 | 30 个 300 s 窗口，每 3 个窗口连续运行900 s，共16200个服务决策 |
| 训练场景种子 | 51000-51009；是场景种子，不是10次独立训练 |
| 验证 | 31500、31501，初始和每6窗口，各运行300 s |
| 最终评估 | 32500、32501、32502，各连续900 s |
| 权重选择 | 固定预算结束的 final，不选 best |
| 时间止损 | 每臂最多1500 s的运行预算，在完整900 s流之间检查；超预算标INCOMPLETE，不与完整臂排名 |

同一当前初始化意味着初期动作依然可能过度分散；本次没有同时改变动作参数化来“救结果”。

## 尚存的实现差别

- 原实现 Critic 损失是两头 MSE 的和；SB3 是该和的0.5倍。固定 batch 梯度检查按这个已知倍数核对。
- 原实现进行梯度范数裁剪（1）；SB3 原生 SAC 不做此裁剪。
- 两者温度更新、随机动作采样的顺序及 tanh Jacobian 的 epsilon 处理有差别。
- 网络初始化与优化器 eps 已匹配；两臂更新次数、数据量须在 report 中再核实。

因此这次是“原更新实现 vs 固定版本库更新”的对照，不是单独证明某一细节因果作用。相较上一轮 pilot，两臂共同改变更新密度、学习率、Actor 延迟和 warmup；即使都变好，也不能单独归功于增加更新次数。

## 读数与下一步

同时报告高/低优时延、10:1加权完成任务时延、任务完成率、期末上传/转发/计算总队列、末段队列斜率和最老未完成任务年龄。只报 completed-only 时延可能掩盖未完成任务，不允许单独据此判成功。

报告每个测试种子，并计算 SB3 减原实现的配对差。只有1个训练种子，3个测试场景的CI不代表训练稳健性，也不能证明无限时域稳定。

- 固定 batch 不一致：停在接口和公式层修复。
- 只有库实现改善：继续定位更新实现差异，不立即动场景。
- 两臂都改善：说明原试验的训练设置值得怀疑，仍不能直接认定某个超参数为根因。
- 两臂都积压：成熟库也未解决当前预算下的问题，继续分析动作、价值尺度及场景可服务性，不自动扩训或切多智能体。

当前实现不会自动启动联合训练。不得把短跑结束称作收敛。

## 输出

`results/sac_compare/manifest.json` 固定配置及源代码哈希；`fixed_batch_audit.json` 数值核验；两臂各自保存训练CSV、固定评估CSV、逐步队列和路由、final权重；总 `report.json` 保存配对结果、预算一致性和CRN轨迹一致性。

只输出两张新的中文图：微观训练/验证曲线、连续队列/完成率。此次宏观固定，两臂轨迹按设计应相同，不生成一张冒充“新学到协作”的轨迹图。

## 本次实际结果（2026-09-05）

运行已完成，没有追加训练，没有启动 PPO 联训。

- 34 项单元测试通过；独立两臂 smoke 通过。
- 实际 SB3 target 最大误差 0.0000076294，Actor 梯度最大误差 0.0000000596；校正已知2倍系数后的 Critic 梯度误差为0。
- 每臂16200条 transition、15201次 Critic 更新、15201次 Actor 更新；宏观网络权重最大变化为0。
- 原实现臂用时7.10分钟，SB3臂6.68分钟，合计约13.78分钟（不含开发和测试）。
- 三个测试场景的用户轨迹、质心控制轨迹、逐宏观步累计到达任务数逐项相同；运行中15个源文件/配置哈希没有变化。

### 结论

核心SAC公式核验通过；增加更新预算并使用成熟库，没有自动获得低时延、稳定收敛的微观策略。不能据此排除所有实现问题，也不能宣判SAC、场景或MDP没有价值。下一步应针对同状态动作与长期代价的对应关系、Critic对这些动作的梯度做定点核查，而不是立即扩训、换多智能体或把未稳定的下层交给PPO。

### 核验与解释

- 3 MHz基线加权时延、期末积压和完成率与原报告复算最大误差为0；两臂用户/UAV轨迹、质心、逐宏观步累计到达任务数完全一致。
- 策略参数最大变化为0；全部36项单元测试通过，包括观测记录器不改变环境transition的测试。本轮重放约1.12分钟。
- 带宽不足是当前冻结策略的重要性能限制：提高带宽后转发积压近乎消失，时延、完成率和软代价同时改善。不能再只从优化器公式寻找解释。
- 但6 MHz下仍有约208 Mbit平均计算积压，其中约207.67 Mbit为低优队列；低优完成任务仍需18.72秒，尚未达到低时延、稳定服务的目标。不能说带宽是唯一原因，也不能说资源干预修复了训练收敛。
- 冻结网络会对干预后的新队列重新作出路由决策；这是带宽干预的闭环总效应，不是保持每帧执行动作固定的传输时间直接效应。没有给每个已完成任务的等待、传输和计算耗时做可加分解。
- 这轮训练前后U2U带宽一直为3 MHz。历史600多毫秒与当前结果还混有MDP、策略和评估时长变化，不能把跨版本退化全部归因带宽；同口径300秒验证中训练后性能变差的事实仍然存在。

下一步应检查6 MHz下逐UAV计算积压、实际入流和CPU服务量，区分路由失衡与局部计算容量不足。暂不追加长训练，不据此改论文主场景或宣称新HRL性能。

### 分配账本揭示了什么

10 GHz、1000 cycles/bit对应服务期每架10 Mbps计算能力；考虑每10秒有1秒部署暂停，平均容量为9 Mbps。按当时的原始区域负载角色分组，学习策略实际分配到目的UAV的计算工作量如下。这不是该区域自身产生的负载，也不是仅U2U流量。

| 当时的区域角色 | 原始到达经上传后进入路由/Mbps | SAC分配到该目的机/Mbps | 固定均分到该目的机/Mbps |
|---|---:|---:|---:|
| 重载 | 18.91 | 7.94 | 8.20 |
| 中载 | 3.96 | 6.78 | 8.20 |
| 轻载 | 1.72 | 9.87 | 8.20 |

原始轻载机被分到超过其平均容量的工作，低优计算积压最多（按角色分组均值95.88 Mbit）。资源提高到12 GHz后，SAC转而将中载角色分到10.73 Mbps，接近该档平均容量10.8 Mbps；重载角色平均CPU利用率仅56.38%，中载角色94.37%。这表明简单增加总算力不能替代合理分配。

区域角色会随负载切换，角色分组均值不是同一架机器连续900秒的守恒方程。逐架逐0.5秒的原始数据保存在`*_uavs.csv`；另外保存按固定UAV编号分组的汇总。计算与传输队列分别核对守恒：计算队列的入流按整块任务实际入队事件记录，不能将部分已传输字节直接算作可计算任务。

还需修正“转发越多越差”的笼统说法：10 GHz下均分规则实际总转发16.39 Mbps，反而高于SAC的15.71 Mbps，但它将计算工作均匀分到三架UAV，队列与时延明显更低。关键不仅是转发量，更是目的地和后续服务负载。

### 判决边界

- CPU提高使当前冻结SAC时延下降，但固定均分在原10 GHz下就可达到低积压、623 ms。这否定了“剩余性能差只能靠增加CPU解决”的解释，不证明固定均分最优。
- 在10 GHz下，均分的时延、J和功率同时优于SAC，所以不能把SAC退化解释成合理的时延-能耗交换。它尚未学好当前优化目标。
- 均分规则900秒内低积压，不是学习收敛曲线，也不是无限时域队列稳定性的证明。其623 ms不能写成PPO+SAC的结果。
- CPU变化也改变了容量观测和后续队列，冻结SAC会相应改变动作；CPU干预是闭环总效应，不是固定执行路由的纯计算加速。均分规则则不随资源改变路由。
- 三场景配对t区间：CPU12减10为[-2650.14,-1230.66] ms；10 GHz下均分减SAC为[-3571.44,-2454.27] ms；12 GHz下为[-1695.52,-540.66] ms。均排零，但都是同一已训练策略在已使用场景上的诊断，不是多训练种子性能结论。

CPU基线与前一轮6 MHz重放误差为0，权重变化为0，用户/UAV轨迹和逐宏观步累计到达数完全一致。38项测试通过，包括CPU仅改变容量、观测维度保持104维、监测不改变transition、队列流量守恒和固定均分语义。

## 6 MHz 从零预训练与 Critic 等价性修正（2026-09-06）

按作者确认，将候选主场景固定为 6 MHz、10 GHz/架、24.725 Mbps 总期望到达。没有同时改 CPU、负载、奖励、动作集合或学习率。主训练沿用本机 native SAC 的每 20 服务帧更新一次、Actor 延迟两次和每阶段前 100 次 Critic 更新等待期；**这不是此前 SB3 每帧更新对照的同训练配置**，不能直接用两轮结果的差值估计带宽效果。

### 这次实际做了什么

1. 新增 `mainline` 工程入口：从零微观预训练，资格通过才启动 PPO/SAC 同步联训。每六窗口在 33000/33001 验证，最后三次验证作检查；33500–33502 只在最后评估。种子清单、规则、配置及代码哈希运行前落盘。
2. 原分数 Critic 从零运行 60 个 300 s 窗口，连续三个窗口才重置一次场景。得到 32400 条 transition、1571 次 Critic 更新、735 次 Actor 更新。PPO 参数变化为 0。
3. 在最后权重的 256 个训练 replay 状态上做动作等价性核查。全零分数、全 +0.25、全 -0.25 都执行同一均分路由；原 Critic 对它们的预测差绝对均值约 6.98，最大 17.44。动作梯度在不改变路由的逐行平移子空间上的范数比均值为 0.421。不能将这个比例解释为“42% 的性能损失”。
4. 单因素修正为 `Q(s,z)=q(s,P(z))`，两头在线及 target Critic 都读取实际投影；Actor、熵定义和 replay 动作保持不变。新一臂仍从零运行完全相同的 60 窗口、种子和更新预算，没有沿用旧权重或引入教师。
5. 第二臂最后权重的等价动作 Q 差为 0，平移子空间梯度范数比约 1.68e-8，结构一致性问题已消除。但这不保证其他 Q 排序正确或策略最优。

路由输入相对原输入加权时延下降 57.9%，三个场景分别改善 13666.51、16620.62、14528.62 ms。但相对均分仍显著偏高，且未完成积压很重。完成任务平均时延存在删失，不能把表中低于另一臂的时延数字单独当作全部任务收益。

两臂最终判决均为 `MICRO_NOT_QUALIFIED_JOINT_NOT_STARTED`，**没有新的完整 HRL 成功结果，没有新的学习型 UAV 轨迹**。没有按中途较好的窗口选权重，没有延长训练，没有放宽判据。原输入运行含评估约 18.64 分钟，路由输入约 10.92 分钟；仿真中积压规模不同影响运行耗时，不能据此声称算法计算效率提升。

### 场景与学习问题共同作用

均分后的理想单机入流约 8.24 Mbps，含部署暂停的计算容量约 9 Mbps，只有 0.76 Mbps 余量。重载区期望负载 18.975 Mbps，将其向某一目的地的比例提高约 4 个百分点，就可能耗尽这部分余量。这个计算是灵敏度示例，不是精确队列稳定定理。

原输入第六窗口的 33000 验证中，实际分配到 UAV 0/1/2 的工作量约 9.62/7.20/7.86 Mbps；UAV 0 持续过载而其他机器留有余量。当时 Actor 只更新六次，分数绝对值最大约 0.103，没有输出饱和。小偏差在接近容量边界的系统里被队列放大，不应再简单归结为“带宽不足”或“算法形式错误”。

执行路由 Critic 的最终测试，按当时重/中/轻载角色分组，实际目的计算入流约为 4.75/13.55/6.34 Mbps；均分各为 8.21 Mbps。当前中载角色被分到过多工作，另外两种角色仍有余量。角色随阶段轮换，这不是同一编号 UAV 全程固定过载；但足以说明剩余问题仍包含路由分配不合理，而不仅是总带宽。

均分只证明该有限测试下存在可行的低积压策略，不证明场景容易学、全局最优或无限时域稳定。训练预算也只对应 735 次 Actor 更新，不能据此否定纯 SAC 路线。移除等价分数这个拟合负担后仍失败，剩余价值学习、探索、样本更新密度和资源余量的影响尚未分离。

### 工程检查与可复核范围

- 50 项测试通过，含投影与环境逐项一致、自动微分数值检验、等价动作 Q 不变、梯度在平移方向为零、checkpoint 恢复、两阶段更新和诊断不污染 replay。
- 两臂训练期间源代码哈希均未变化；初始 Actor/网络参数匹配测试通过，实际前五窗口的行为也一致。用户轨迹、质心轨迹和逐宏观步累计到达量在各测试对照中一致。
