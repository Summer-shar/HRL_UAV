# G1 停训后的单因素候选探索

本目录只包含独立输出。正式源码、训练配置、网络、物理服务规则和 checkpoint 未改动，未训练、未 resume。

这是第一号固定 dev 场景、每个窗口从空队列开始、60 s 的短窗控制敏感性研究。每套场景均运行悬停／朝需求质心／反向移动 × Local／三等分六个组合；不等同于 20 场景、900 s 的正式 G1，不用于选择新训练场景，也不证明解决 SAC 学习失败。

实际总步数 **19,075**：脚本对照 18,000，参数化原物理合同测试 1,074，独立上传 ledger 精度核验 1。30 个脚本窗口全部完成；控制断言全部通过；学习更新次数为 0。详见 budget.json、summary.json。

## 配对与边界

- 同一候选的六个动作组合具有完全相同的外部到达 SHA256。除负载候选外，四套场景之间的到达签名也完全一致；负载候选保持种子但改变了到达律，不能跨负载把任务一一配对。
- 朝需求控制复用基线的因果权重：过去10 s的已观测到达cycles与当前上传cycles积压，高优×10；按各候选最大位移归一化。控制器不读取未来任务或生成器热点。热点仅用于离线定义偏离起点。
- 反向控制每个上层边界反转当前需求方向。由于后续上传积压不同，它并非推进能量精确匹配的对照；完整运动和能量已保存。
- 60 s是工程诊断采样长度。使用现有collect_metrics截断逻辑，成本在截止时刻记录，合法后继仍按当前物理轨迹生成。窗口末尾未完成任务计入年龄，未提前刷新队列。

## 文件与复现

- scene_g1_candidate_20260928_*.json：五套可加载场景；candidate_manifest.json列出每套相对原版的精确字段变化和文件SHA256。其他字段保留原版，status或说明字符串本身不代表研究验收。
- run_candidate_study.py：生成候选并先运行50条原物理合同；保留了遇到上行严格断言失败时退出的原行为。study.stderr.log和contracts_*.txt是原执行记录。
- continue_candidate_study.py：仅接受完整的上述1,074步初始证据，补1步独立精度核验并执行30个窗口；拒绝自动重复运行或覆盖case数据。continuation.*.log为实跑记录。
- 在同层级的新空输出目录复制两个脚本后，依次用项目.venv/Scripts/python.exe执行它们，可以复现本次包括原失败在内的流程；不要在本证据目录重新执行。任何复现均有单独物理步数预算。
- plan.json保存源码身份和首个脚本SHA256；summary.json确认运行前后所有src Python文件及训练/场景配置SHA256一致。
