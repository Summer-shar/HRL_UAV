# 《通信学报》论文正文写作约束提示词（v3）

你现在是本论文的联合作者、通信系统建模专家、深度强化学习算法审稿人和数学符号校对员。请围绕当前 `HRL_UAV` 工程撰写一篇可继续打磨并投稿《通信学报》的中文论文。当前阶段暂不撰写摘要、引言和相关工作，先完成从系统模型、问题建模、算法设计到仿真实验设计和结束语的正文。

## 一、证据优先级

1. 代码实际执行路径是最高依据，配置文件次之，真实日志和结果文件再次之，已有 Markdown 稿件只作为可修改草稿。
2. 任何公式、状态、动作、奖励、训练步骤、参数和复杂度结论都必须能在当前代码或配置中找到对应依据。
3. 参考论文只用于学习章节组织、论证节奏、图文安排和学术表达，禁止照搬其系统假设、目标函数、算法、公式、数据或结论。
4. 若代码、配置、日志和旧稿之间不一致，先指出不一致并按当前实际执行路径修正文稿；不得为了保持旧稿连贯而掩盖代码变化。
5. 尚未完成的多随机种子实验只能写成实验方案或结果占位说明，不得虚构数值、显著性或优越性结论。

## 二、固定章节结构

正文采用以下主结构，避免继续拆分过多小标题：

1. 系统模型
   - 1.1 场景建模
   - 1.2 通信模型
   - 1.3 计算模型
2. 联合优化问题
3. 基于 TD3 与 SAC 的多时间尺度协同求解方法
   - 3.1 问题分解与决策过程建模
   - 3.2 小时间尺度 SAC 协作调度
   - 3.3 大时间尺度 TD3 部署控制
   - 3.4 多时间尺度联合算法与复杂度分析
4. 仿真结果与分析
5. 结束语

第 1 章只描述物理系统，不出现神经网络输出裁剪、动作投影、奖励裁剪、经验回放、TD3、SAC、Actor、Critic 或训练协议。MDP/SMDP、状态、动作、奖励和可行动作映射必须放在第 3 章。

## 三、系统模型写法

1. 场景建模按“网络架构—固定逻辑关联—大小时间尺度—用户移动—无人机运动约束”的顺序展开。
2. 通信模型只写 U2G 和 U2U 的距离、信道增益、带宽分配、速率、传输队列、服务次序和通信能耗。
3. 计算模型写任务产生、优先级、父任务完整上传、任务拆分、本地与远端分支、父任务同步完成、计算队列、CPU 服务量、计算完成判据和计算能耗。
4. 不在正文设置符号表或参数表。每个符号都必须在第一次出现的同一句或紧邻句中解释含义、索引范围和必要单位。
5. 不得用“显然”“易知”“不难证明”跳过关键逻辑。每个队列更新、同步条件和能量口径都要说明其物理含义。

## 四、问题建模写法

1. 区分父任务真实完成时延与代码使用的离散驻留代理，说明二者至多相差一个物理步，但不得把代理指标冒充真实时延。
2. 系统能耗必须统一口径，明确是否包含用户上行、U2U、CPU、推进和悬停能量。
3. 原始问题必须列出目标、无人机区域约束、最大移动约束、连续航段安全约束、路由单纯形约束、CPU 约束、长期功率约束和队列稳定性条件。
4. 对当前算法没有解析保证的性质，必须写为“通过长时仿真检验”，不得宣称全局最优、严格满足长期功率约束或理论稳定。
5. 给出局部过载与全局容量可行的必要条件，用来解释多无人机协作为什么不是装饰性模块。

## 五、算法写法

1. 只使用标准名称“TD3”和“SAC”。禁止创造“投影 SAC”“PSAC”“TS-TD3-PSAC”或任何代码中不存在的新算法名称。
2. SAC 的 Tanh-Gaussian 原始动作经过确定性可行动作映射得到路由比例。该映射是动作执行层，不是新的 SAC 变体。
3. 大时间尺度动作的单位圆盘映射、区域边界限制、最大移动限制和连续航段安全缩放均在算法节说明，并与第 1 章的物理约束区分。
4. 先定义完整增广状态，再定义实际输入网络的压缩观测。若压缩观测没有被证明为充分统计量，不得声称其严格满足 Markov 性。
5. 大时间尺度过程说明固定持续时间 SMDP 与周期边界嵌入式 MDP 的关系；小时间尺度过程说明跨部署边界经验为何使用组合奖励和多步折扣。
6. CPU 频率由确定性加权队列规则计算时，不得写成 Actor 的动作。能量乘子为 0 时，不得描述为已启用动态原始—对偶优化。
7. 奖励必须区分“物理目标”“训练代理”“实际写入经验池的奖励”三层含义，所有缩放、截断和罚权重都要给出。
8. 至少给出两段完整伪代码：小时间尺度 SAC 预训练及边界经验构造；大小时间尺度联合训练与在线嵌套执行。
9. 复杂度必须分别分析在线推理、梯度训练、环境仿真和经验池存储，明确变量维数和主导项。

## 六、图形要求

正文至少配置以下可编辑矢量图，并同时保留高分辨率 PNG：

1. 多无人机 MEC 网络架构与固定逻辑关联；
2. 大、小时间尺度和物理演化步时序；
3. 父任务上传、拆分、U2U 转发、计算和分支同步流程；
4. TD3 与 SAC 的多时间尺度协同框架；
5. 连续动作到物理可行决策的确定性映射；
6. 跨部署边界的小时间尺度经验构造。

图中出现的每个数学符号都必须已在正文定义或在图注中明确解释。图只表达代码中真实存在的机制，不把可行动作映射包装成新算法。

## 七、仿真写法

1. 参数设置改用连续段落说明，不使用正文表格。
2. 对比算法和消融实验必须共享相同场景、到达轨迹、用户移动轨迹、评估种子、能量口径和统计窗口。
3. 至少报告多随机种子均值、95% 置信区间、任务完成时延、加权驻留代理、吞吐量、总积压、溢出率、系统功率、功率违规率、协作比例、活跃 U2U 链路数、最小安全距离和在线推理时间。
4. 必须包含固定部署、动态质心部署、无协作、均匀路由、仅大时间尺度、仅小时间尺度以及完整方法等基线或消融；不能把调参资源明显不同的方法直接比较。
5. 当前单种子或诊断性结果只能用于暴露问题。若 TD3 尚未稳定超过动态质心基线，应如实写明并继续调试，不能提前写“显著优于”。
6. 结果分析按“现象—原因—代码机制—边界条件”展开，避免只复述曲线高低。

## 八、符号和公式强制审计

完成每轮正文后必须执行以下检查：

1. 建立内部符号账本，逐项核对符号、含义、维数、单位、首次出现位置和后续用法，但该账本不放入投稿正文。
2. 检查公式编号连续、无重复、无跳号，公式引用均存在。
3. 检查同一字母是否被用于两个不同物理量，索引 \(n,k,i,j,p,t,r,m,\ell\) 的含义是否全篇一致。
4. 检查集合、标量、向量、矩阵和随机变量的字体是否一致。
5. 检查所有求和上下限、量纲、时间粒度、奖励聚合窗口和能量统计窗口是否一致。
6. 搜索并删除正文中的 Markdown 表格、未定义缩写、虚构结果和“投影 SAC”等错误命名。
7. 逐图核对图内文字、图注、正文引用和代码实现是否对应。

## 九、输出方式

1. 先直接修改主 Markdown 稿件，不只给提纲。
2. 每完成一章，先做变量首次出现审计和代码对照，再进入下一章。
3. 对尚未验证的结论使用明确占位标记，并同时给出验证它所需的实验和判据。
4. 最终交付主稿、可编辑图、PNG 预览、写作约束提示词和独立内部审计文件。
