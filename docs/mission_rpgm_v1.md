## 启用与兼容

`environment.motion_protocol` 缺失或等于 `legacy_fly_hover` 时保持原语义。
候选模式须显式传入以下增量；实际完整有效配置见结果 manifest：

```json
{
  "motion_protocol": "mission_rpgm_v1",
  "deployment_dt": 0.0,
  "pause_service_during_flight": false,
  "deployment_transient_energy_mode": "none",
  "mission_duration_s": 900.0,
  "mission_routes_m": [
    [[350, 350], [620, 430]],
    [[350, 650], [620, 650]],
    [[650, 500], [900, 400]]
  ]
}
```

这是无单独部署暂停的完整连续模式，并非在旧协议中仅关闭暂停开关。
沿用来源的 `compute_during_deployment=true`，但新模式没有部署帧，CPU在全部物理步服务。
当前实现要求三架UAV、原固定来源锚点、RPGM、非静态用户、0.5秒资源/到达帧、
无部署瞬态能量；非法模式、路线或不兼容组合报错。
6 MHz候选无线、10 GHz CPU及来源的其他物理参数不变。

每组参考中心沿指定直线用900秒迁移，之后参考中心保持终点。
群内随机运动、原边界处理和用户来源关联保留。为避免额外改变到达随机流，
保留原群运动随机抽样的消耗顺序，再用确定性任务路线速度替换群速度。
业务质心仍由当前用户与任务负载产生，不等同于群参考中心。
本次只运行前60秒，没有加速路线，也没有验证终点附近的长期边界行为。

## 三时间尺度与任务流水

1. 每10秒：原 rollout 结算上个宏观周期，推进负载阶段，准备当前到达/质心和因果质心速度，再读取宏观观测并决定位移。
2. 每0.5秒：更新群/个体运动速度，生成当前到达并更新业务质心，SAC读取观测并给出路由分数。
3. 每0.1秒：先保存此前已上传完成的任务列表；按步首几何执行上传；只路由该保存列表；执行CPU服务；执行U2U；最后积分用户/UAV位置并推进时钟。

因此，本步上传完成的任务下一物理步才可路由，本步U2U完成的远端分片下一物理步才可计算。
U2G与U2U在同一步使用相同的步首几何；U2U仍按实际队列、带宽与发射功率预算服务。
新模式每macro有20次SAC决策，没有旧模式的两帧部署间隙。

宏观动作是6维世界坐标分数：逐分量裁剪到[-1,1]，每架二维向量投影到单位圆盘，乘20米。
随后仍经过地图限制与原整段路径安全处理；实际位移除以10秒得到匀速。
零动作是原地悬停，不是质心跟踪；不使用旧局部60米残差或旧小位移死区。
位置在100个物理步中积分，不直接改坐标瞬移。末步只消除1e-8米容差内的积分舍入误差。

SAC观测/动作维数仍是68/18，宏观观测仍是67维。没有加入UAV速度等新特征，
不能仅凭维数一致声称旧SAC已具备连续运动适应性，更不能迁移旧宏观权重。

经验边界复用原 `boundary_reward()`：空部署列表使跨macro后继经验折扣为gamma，
不再是旧两部署帧的gamma立方。宏观奖励仍是20帧原折扣奖励的均值，
宏观折扣仍为 `gamma**20`（gamma=0.99时约0.817907）。
测试以无网络替身核对真实rollout、后继观测、边界与尾部统计；未修改学习数学。

## 推进与盲巡航

对每架UAV，v是实际位移长度除以10秒，P(v)沿用原旋翼功率函数，单位W。
完整推进能量为 `10*P(v)` J，原目标中的相对悬停增量为 `10*(P(v)-P(0))` J。
二者分别按100个物理步分摊，完整平均功率保留全部推进能量，J保留带符号增量。
没有截断负增量，也没有逐macro追加 `0.5*m*v**2`。

这是准稳态速度模型，忽略宏观边界加减速与转向附加能耗，不是已经验证的硬件模型。
独立标量算例与环境公式一致：P(0)约194.763445 W，P(2)约189.638620 W。

五个预先固定的控制器：

| 控制器 | 下一10秒目标/位移 |
|---|---|
| Hover | 位移0 |
| Current centroid | 当前业务质心减当前位置 |
| Progressive centroid | 上述位移乘固定0.5 |
| Predictive centroid | 当前业务质心加10秒历史质心速度领先量，再减当前位置 |
| Blind Patrol | 全部UAV先沿世界x正向2 m/s运行30秒，再反向30秒；只读调用次数 |

所有规则通过同一位移与安全接口。预测规则没有读取未来位置或路线终点。
盲巡航不读取用户、队列、信道或业务状态，仅作物理退化诊断，不作为论文算法基线。
原 rollout 的 `macro_enabled=true` 在这里仅让固定控制器输出动作，不实例化PPO。

## 短程结果与停止

场景33600，各60秒，从空队列开始；J是原物理代价均值，不是完成任务时延。

| 控制器 | J | 驻留项 | 能量项 | 完整平均功率/W |
|---|---:|---:|---:|---:|
| Hover | 0.543814 | 0.378255 | 0.165559 | 816.073 |
| Current centroid | 0.538756 | 0.375330 | 0.163426 | 813.086 |
| Progressive centroid | 0.540398 | 0.375645 | 0.164753 | 814.944 |
| Predictive centroid | 0.535746 | 0.374970 | 0.160776 | 809.376 |
| Blind Patrol | 0.542877 | 0.388110 | 0.154767 | 800.964 |

盲巡航相对Hover：驻留项增加0.009855，能量项减少0.01079222，J净减少0.00093722（约0.172%）。
三架合计推进能量减少922.468 J，等效60秒平均推进功率减少15.374 W。
高/低优完成时延反而分别增加约9.170/10.325 ms。
五种控制器高优完成率均为1，低优均约0.992736；这不是全部任务完成或长期稳定证明。

因此确实出现“服务驻留更差，但靠能量抵消后小幅优于Hover”的短程风险信号。
它仍比三个追踪规则的J更高，不能称为盲巡航压倒合理追踪，也不能据此断言PPO必然学会巡航。
反过来，追踪胜过盲巡航也不证明其收益全部来自通信或队列。
首次smoke结束时已停止，没有调速度、截负能量、加约束、训练PPO或扩展评价。
